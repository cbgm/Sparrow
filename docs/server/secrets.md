# Server secrets and signing material

Never commit production secret values.

## What belongs here

Release/production server deployments may require material such as:

- Firebase Admin service-account JSON (FCM push and phone-token verification on the Control Plane);
- registry root and registry authority identity/certificate (generated by the Control Plane launcher);
- generated registry signing state;
- database passwords/internal API tokens depending on deployment mode.

In an installation created by the server installer, `control-plane/secrets/` holds the generated registry trust material and other generated secrets; the installer reuses them on every Start. Operators select the Firebase Admin JSON in the installer (**Push notifications and phone verification**, or `--firebase-file`). It is stored outside the bundle on Windows (`%LOCALAPPDATA%\Sparrow\Server\Secrets\<control-plane-id>\firebase-admin.json`) and as `control-plane/secrets/firebase-admin.json` on Linux/macOS, and mounted read-only into `push` and `presence-directory` through `docker-compose.firebase.yml`. The service account needs FCM and Firebase Authentication access to the app's Firebase project (`FIREBASE_TARGET_PROJECT_ID`, default `sparrow-a9048`).

## Repository helper

For the repository production stack, `server/scripts/New-ProductionSecrets.ps1` can generate ignored secret files/environment configuration used by the Compose setup.

```powershell
.\server\scripts\New-ProductionSecrets.ps1
```

Generated secret files are deliberately ignored by Git.

## Release signing is separate

Android release signing secrets are **not server secrets**. The release workflow uses GitHub Actions Secrets `KEY_STORE_FILE`, `KEY_STORE_PASSWORD`, `KEY_ALIAS`, and `KEY_PASSWORD`. `KEY_STORE_FILE` contains the Base64-encoded keystore. Do not put the Android `.jks` into this directory or commit it.
